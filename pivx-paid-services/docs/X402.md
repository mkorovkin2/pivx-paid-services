# x402 follow-up mapping

This release does not implement an x402 facilitator, HTTP 402 header negotiation, `/supported`, `/verify` or `/settle`.

| Current operation | Future adapter boundary |
| --- | --- |
| `get_quote`, `create_invoice` | Build payment requirements: exact integer amount, PIV asset/network identifier, shielded payTo and `extra.memo` |
| Agent Kit `pivx_send` | Buyer submits a real shielded payment with the encrypted invoice memo |
| Receiver reconciliation and `check_invoice` | Verify the receiver actually decrypted the memo-bound note, amount, canonical inclusion, confirmation tier and unique receipt identity |
| Persisted paid entitlement | Map successful verification to a settlement/authorization result without replaying fulfillment |
| `call_service` request ID and stored result | Retry-safe resource delivery scoped to the paid entitlement |

A claimed transaction ID is insufficient proof of shielded payment. Verification remains server-side against the receiver and canonical chain. The memo is private payment metadata and must not appear in the public dashboard. Receipt deduplication must survive any future transport adapter and process restarts.

The exact version-specific headers and asset/network identifiers require design against the selected x402 specification in that follow-up. This document describes the conceptual boundary rather than claiming protocol compatibility today.
